# 개념 설명서 — ④ 박준영

[개발 지침서](14_개발지침서_④박준영.md)의 단계마다 나오는 개념을 같은 번호로 설명한다.
지침서에서 막히거나 "이게 왜 이렇게 되지?" 싶을 때 같은 번호를 찾아 읽는다.
단계 끝의 **말로 설명해 보기**는 교수님 질문에 대비한 연습이다. 코드를 보지 않고 소리 내어 답해 본다.

더 기초적인 개념(필드, 행, PK, FK, SQL)은 [04 기초 개념 정리](../04_기초개념정리.md)에 있다.

## 1단계 — 프로젝트, 패키지, 클래스

**프로젝트**: 프로그램 하나를 이루는 파일 전체를 담는 큰 상자. 우리는 `DicePOS` 하나를 6명이 같이 쓴다.

**패키지**: 클래스를 담는 폴더. 이름을 점(.)으로 이어 쓴다.

| 패키지 | 들어 있는 것 | 담당 |
|---|---|---|
| `dicepos.common` | 모두가 쓰는 도구 (DB 연결, 안내창, 로그인 정보) | ④ ① ⑤ |
| `dicepos.main` | 프로그램 시작, 메인 창 | ④ ③ |
| `dicepos.menu` | 메뉴 관리, 발주 관리 | ④ |
| `dicepos.game` | 보드게임 | ③ |

**클래스**: 한 가지 일을 맡는 코드 묶음. 파일 하나에 클래스 하나, 파일 이름과 클래스 이름이 같아야 한다 (`MenuPanel.java` 안에 `class MenuPanel`).

**import**: 다른 패키지의 클래스를 쓰겠다고 맨 위에 적는 줄. 빨간 줄이 나면 `Ctrl + Shift + O`로 자동으로 채울 수 있다.

**jar와 Build Path**: jar는 다른 사람이 만든 클래스를 묶어 놓은 파일이다. Java는 혼자서 MySQL과 말할 줄 모르기 때문에, MySQL 회사가 만든 통역사(`mysql-connector-j`)를 Build Path에 넣어 준다.

**UTF-8**: 글자를 저장하는 방식. Windows Eclipse는 기본이 다른 방식이라 한글이 깨질 수 있어서 처음에 UTF-8로 맞춘다.

**말로 설명해 보기**
- 패키지는 왜 나눴나요? → 담당자별로 파일이 섞이지 않게, 그리고 같은 이름의 클래스가 부딪히지 않게.

## 2단계 — DB 연결 (JDBC)

**JDBC**: Java에서 DB를 쓰는 표준 방법. 순서는 항상 같다.

```
연결(Connection) → SQL 준비(PreparedStatement) → 실행 → 결과 읽기(ResultSet) → 닫기
```

**Connection**: Java와 MySQL 사이의 전화선 하나. `DriverManager.getConnection(주소, 아이디, 비밀번호)`로 연다.

**주소(URL) 읽는 법**: `jdbc:mysql://localhost:3306/dicepos?serverTimezone=Asia/Seoul&characterEncoding=UTF-8`

| 부분 | 뜻 |
|---|---|
| `localhost` | 내 컴퓨터 |
| `3306` | MySQL이 기다리는 번호(포트) |
| `dicepos` | 쓸 DB 이름 |
| `serverTimezone=Asia/Seoul` | 시간을 한국 시간으로 |
| `characterEncoding=UTF-8` | 한글을 깨지지 않게 |

**DBUtil을 따로 만든 이유**: 주소와 비밀번호를 한 곳에만 적기 위해서다. 비밀번호가 바뀌어도 이 파일 하나만 고치면 6명의 화면이 모두 따라간다.

**try-with-resources**: `try ( … )` 괄호 안에서 연 것은 끝나면 자동으로 닫힌다. 닫지 않으면 전화선이 쌓여서 나중에 DB가 더 이상 연결을 받지 않는다.

**SQLException**: DB에서 문제가 생기면 던져지는 예외. `catch`로 받아서 화면에 안내한다.

**말로 설명해 보기**
- DB 접속 정보를 왜 DBUtil 한 곳에만 두었나요?
- Connection을 닫지 않으면 어떻게 되나요?

## 3단계 — static 도구 메서드

**static 메서드**: 객체를 만들지 않고 `클래스이름.메서드()`로 바로 부르는 메서드. `UIUtil.won(3000)`처럼 쓴다. 상태를 기억할 필요가 없는 도구에 알맞다.

**JOptionPane**: Swing이 미리 만들어 둔 안내창.

| 메서드 | 모양 | 우리 이름 |
|---|---|---|
| `showMessageDialog` | 글과 [확인] 버튼 | `UIUtil.warn`, `UIUtil.info` |
| `showConfirmDialog` | [예] [아니요] | `UIUtil.confirm` (예면 true) |

**DecimalFormat("#,###")**: 숫자를 `3,000`처럼 세 자리마다 쉼표를 찍어 준다.

**Integer.parseInt와 예외**: 글자 `"3000"`을 숫자 3000으로 바꾼다. `"abc"`처럼 숫자가 아니면 `NumberFormatException`이 난다. `UIUtil.toInt`는 그 예외를 잡아서 `null`을 돌려준다. 그래서 화면에서는 `null`인지만 보면 된다.

**int와 Integer**: `int`는 숫자만 담을 수 있고, `Integer`는 숫자 또는 `null`(값 없음)을 담을 수 있다. "숫자가 아님"이나 "보드게임이라 메뉴 번호 없음"을 표현할 때 `Integer`를 쓴다.

**말로 설명해 보기**
- 가격 칸에 글자를 넣으면 프로그램이 멈추지 않고 어떻게 안내하나요?

## 4단계 — 임시 파일 (스텁)

**스텁(stub)**: 진짜가 오기 전까지 자리를 지키는 가짜 클래스. 이름, 패키지, 메서드 모양(이름·받는 값·돌려주는 값)만 진짜와 같게 만든다.

**왜 필요한가**: 내 발주 화면은 ③의 `GameDAO`와 ①의 `Session`을 쓴다. 이 둘이 없으면 내 코드가 컴파일되지 않는다. 스텁을 두면 팀원을 기다리지 않고 내 화면을 먼저 완성하고 시험할 수 있다.

**약속이 중요하다**: 스텁의 메서드 모양이 팀원의 진짜 클래스와 다르면 13단계에서 빨간 줄이 생긴다. 그래서 개인 개발 문서에 적힌 메서드 이름(`GameDAO.findAll()`, `increaseStock(Connection, gameId, qty)`, `Session.getAdminId()`)을 팀원과 미리 맞춘다.

**말로 설명해 보기**
- 다른 팀원의 클래스가 아직 없는데 어떻게 시험했나요?

## 5단계 — 창과 화면 전환 (Swing)

**JFrame**: 창 하나. `PosMainFrame`이 `extends JFrame`이라서 "창의 기능을 다 갖고, 내 것을 더한" 클래스가 된다(상속).

**JPanel**: 창 안에 넣는 판. 팀원 화면은 모두 JPanel이다.

**배치관리자 (판 안에 부품을 놓는 규칙)**

| 이름 | 놓는 방식 | 메인 창에서 |
|---|---|---|
| `BorderLayout` | 동·서·남·북·가운데 | 왼쪽(WEST)에 메뉴, 가운데(CENTER)에 화면 |
| `CardLayout` | 여러 장을 겹쳐 두고 한 장만 보여 줌 | 팀원 화면 전환 |
| `GridLayout(0, 1)` | 같은 크기로 한 줄에 하나씩 | 메뉴 버튼 세로 줄 |
| `BoxLayout` | 위에서 아래로 차례대로 | "직원 화면" 글자 → 버튼들 → "관리자 화면" 글자 → 버튼들 |

**addScreen의 원리**: `center.add(화면, 이름)`으로 카드에 이름을 붙여 넣고, 버튼을 누르면 `cards.show(center, 이름)`으로 그 카드를 앞으로 꺼낸다. 그래서 팀원은 `addScreen` 한 줄만 쓰면 메인 창에 붙는다.

**관리자 잠금 흐름**
```
관리자 버튼 클릭 → 잠겨 있나? ─ 예 → 관리자 확인 팝업(①) → 통과하면 Session에 관리자 번호 기억
                               └ 아니요 → 바로 화면 보여 줌
직원 버튼 클릭 → Session.lockAdmin() → 다시 잠금
```

**람다 `e -> open(name, admin)`**: "버튼이 눌리면 이 코드를 실행해"를 짧게 쓴 것. `ActionListener`를 따로 클래스로 만들지 않아도 된다.

**SwingUtilities.invokeLater**: Swing 화면은 이벤트 처리 전용 줄(EDT) 하나가 그린다. 프로그램 시작 코드도 그 줄에 맡겨야 화면이 꼬이지 않는다.

**말로 설명해 보기**
- 6명이 만든 화면을 한 창에 어떻게 합쳤나요?
- 직원 화면으로 돌아오면 관리자 화면이 왜 다시 잠기나요?

## 6단계 — DTO와 DAO

**DTO (Data Transfer Object)**: DB 한 줄을 담는 그릇. `MenuDTO` 하나가 menu 테이블의 한 줄이다. 필드는 `private`으로 숨기고 `getXxx()`로만 꺼낸다(캡슐화).

**DAO (Data Access Object)**: 한 테이블의 SQL을 모아 둔 클래스. 화면은 SQL을 모르고, DAO에게 "메뉴 목록 줘"라고만 부탁한다.

```
MenuPanel(화면) ──부탁──▶ MenuDAO ──SQL──▶ MySQL
       ▲                     │
       └──── List<MenuDTO> ──┘
```

**나눈 이유**: 화면을 바꿔도 SQL은 그대로, SQL을 바꿔도 화면은 그대로다. 그리고 "menu를 바꾸는 SQL은 MenuDAO에만 있다"는 팀 규칙을 지킬 수 있다.

**PreparedStatement와 `?`**: SQL의 값 자리를 `?`로 비워 두고 `setString`, `setInt`로 채운다. 글자를 이어 붙이지 않으므로 SQL 인젝션을 막고, 따옴표를 신경 쓰지 않아도 된다.

**executeQuery와 executeUpdate**

| 메서드 | 쓰는 SQL | 돌려받는 것 |
|---|---|---|
| `executeQuery()` | SELECT | `ResultSet` (결과 표) |
| `executeUpdate()` | INSERT, UPDATE, DELETE | 바뀐 줄 수 (int) |

**ResultSet**: SELECT 결과를 한 줄씩 읽는 손가락. `while (rs.next())`로 다음 줄로 넘어가고 `rs.getString("name")`으로 칸을 읽는다.

**자동 생성 키**: `Statement.RETURN_GENERATED_KEYS`를 주고 INSERT하면 DB가 만든 번호(AUTO_INCREMENT)를 `getGeneratedKeys()`로 돌려받는다.

**말로 설명해 보기**

- SQL에 값을 바로 이어 붙이지 않고 `?`를 쓰는 이유는?

## 7단계 — 메뉴 관리 화면

**JTable + DefaultTableModel**: 표는 보이는 것(JTable)과 데이터(Model)가 따로 있다. `model.setRowCount(0)`으로 비우고 `model.addRow(...)`로 채우면 표가 따라 바뀐다. `isCellEditable`을 `false`로 해서 표에서 직접 못 고치게 했다. 고치는 것은 오른쪽 폼에서만 한다.

**ListSelectionListener**: 표의 줄을 고르면 실행된다. 마우스를 누르는 동안에도 여러 번 불리기 때문에 `getValueIsAdjusting()`이 false일 때(다 고른 뒤)만 폼을 채운다.

**ItemListener와 `filling` 깃발**: 품절 체크박스는 바뀔 때마다 DB에 저장한다. 그런데 표를 골라 폼을 채울 때도 체크박스가 바뀐다. 이때는 저장하면 안 되므로 `filling = true`인 동안은 무시한다.

**GridBagLayout**: 칸 크기가 서로 다른 입력 폼에 쓰는 배치. `gridx`, `gridy`로 몇 번째 칸에 놓을지 정한다. (라벨은 0열, 입력칸은 1열)

**입력 검사 → DB 검사 순서**
1. 화면에서 먼저 막는다: 빈 이름, 숫자가 아닌 가격, 0 이하 가격, 음수 재고
2. DB가 막는 것은 예외로 받는다: 같은 이름(UNIQUE) → `SQLIntegrityConstraintViolationException`(오류 1062) → "이미 있는 메뉴 이름입니다."

**재고 0이면 자동 품절**: 저장할 때 `soldOut = 체크 || stock == 0`

**삭제 전에 세 곳을 확인하는 이유**: 주문 상세(⑥), 결제 상세(②), 발주 상세(④)가 menu를 FK로 가리킨다. 하나라도 있으면 DB가 삭제를 막는다(오류 1451). 그래서 먼저 `countUsage`로 세어 보고, 있으면 "품절로 바꾸세요"라고 안내한다. 지난 주문과 결제 기록을 지키기 위해서다.

**TableCellRenderer**: 표의 칸을 어떻게 그릴지 정하는 클래스. `SoldOutRenderer`는 품절 줄의 글씨를 회색으로 그린다.

## 8단계 — 발주 DTO

**발주를 두 개로 나눈 이유 (헤더 + 상세)**: 발주 한 번에 여러 품목을 주문한다. 발주 1건(누가, 언제, 어디에, 총액, 상태)은 `purchase_order`에 1줄, 품목마다 `purchase_order_detail`에 1줄씩 저장한다. 결제·주문과 같은 방식이다.

**ItemOption과 toString**: 콤보박스는 넣은 객체의 `toString()` 결과를 글자로 보여 준다. `ItemOption`은 이름만 보여 주고, 속에는 구분(메뉴/보드게임)과 번호를 갖고 있어서 고르면 번호를 바로 꺼낼 수 있다.

**menuId와 gameId가 Integer인 이유**: 메뉴를 발주하면 gameId가 없고, 보드게임을 발주하면 menuId가 없다. "없음"을 `null`로 표현해야 해서 `Integer`를 쓴다. DB에도 NULL로 저장된다.

**금액은 계산해서 돌려준다**: `getAmount()`가 `qty * unitCost`를 계산한다. 수량이 바뀌어도 금액이 자동으로 맞는다.

**매입 단가(unitCost)와 판매 가격(price)은 다르다**: 단가는 사 올 때 값이고 발주마다 바뀔 수 있어서 상세에 그때 값을 저장한다.

## 9단계 — 트랜잭션

**트랜잭션**: 여러 SQL을 "전부 성공 아니면 전부 취소"로 묶은 한 덩어리.

```java
con.setAutoCommit(false);   // 1. 묶기 시작 (이제 바로 저장되지 않음)
… INSERT / UPDATE 여러 개 …
con.commit();               // 2. 전부 성공하면 한꺼번에 확정
// 중간에 예외가 나면 catch에서
con.rollback();             // 3. 처음부터 전부 없던 일로
// finally에서
con.setAutoCommit(true); con.close();   // 4. 원래대로 하고 닫기
```

**발주 요청을 묶는 이유**: 발주(헤더)는 저장됐는데 품목(상세)이 실패하면 "품목 없는 빈 발주"가 남는다. 묶으면 둘 다 저장되거나 둘 다 안 된다.

**입고를 묶는 이유**: 상태는 '입고'로 바뀌었는데 재고는 그대로인 상황을 막는다.

**오류가 나도 저절로 취소되지 않는다**: 앞에서 실행한 INSERT는 살아 있다. 그래서 `catch`에서 반드시 `rollback()`을 부른다.

**같은 Connection을 넘기는 이유**: 트랜잭션은 Connection 하나에 묶인다. 입고할 때 ③의 `GameDAO.increaseStock(con, …)`에 **내 con**을 넘겨야 게임 재고 변경도 같은 덩어리가 된다. ③이 새 Connection을 열면 따로 저장돼 버린다.

**조건 붙은 UPDATE로 두 번 막기**: `… WHERE po_id = ? AND status = '요청'`. 이미 입고된 발주는 조건에 안 맞아서 바뀐 줄이 0이 된다. 그러면 예외를 던져 [입고]를 두 번 눌러도 재고가 두 번 늘지 않는다. 취소도 같은 방식이다.

**setObject(…, null, Types.INTEGER)**: `setInt`에는 null을 넣을 수 없어서, null일 수 있는 menuId·gameId는 `setObject`로 넣는다.

**SQL 몇 가지**

| SQL | 뜻 | 쓴 곳 |
|---|---|---|
| `LEFT JOIN staff` | 직원 정보가 없어도 발주는 보여 줌 | 발주 내역 |
| `COUNT(d.po_detail_id)` + `GROUP BY` | 발주마다 품목 수 세기 | 발주 내역 |
| `COALESCE(m.name, g.name)` | 메뉴 이름이 없으면 게임 이름 | 발주 상세 |
| `ORDER BY … DESC LIMIT 1` | 가장 최근 것 하나 | 직전 단가 |

## 10단계 — 팝업 (JDialog)

**JDialog**: 창 위에 뜨는 작은 창.

**모달(modal)**: `ModalityType.APPLICATION_MODAL`이면 팝업을 닫기 전까지 뒤 화면을 누를 수 없다. 그리고 `setVisible(true)`에서 코드가 멈춰 기다린다. 그래서 `confirm()`은 팝업이 닫힌 뒤 사용자가 [입고]를 눌렀는지(`ok`)를 바로 돌려줄 수 있다.

**dispose()**: 팝업을 닫고 정리한다.

**말로 설명해 보기**
- 입고 확인 팝업이 떠 있는 동안 뒤 화면을 못 누르는 이유는?

## 11단계 — 발주 관리 화면

**JToggleButton + ButtonGroup**: 눌린 상태가 유지되는 버튼. 같은 ButtonGroup에 넣으면 둘 중 하나만 눌린다([메뉴] / [보드게임]).

**JSpinner**: 위아래 화살표로 숫자를 바꾸는 칸. `SpinnerNumberModel(처음 1, 최소 1, 최대 999, 1씩)`이라 0이나 음수를 넣을 수 없다.

**장바구니(cart)는 ArrayList**: [발주 요청]을 누르기 전까지는 DB가 아니라 메모리의 `List`에만 담는다. 중간에 바꾸거나 비워도 DB가 지저분해지지 않는다.

**같은 품목은 수량만 합치기**: 담을 때 cart를 돌면서 구분과 번호가 같은 품목이 있으면 `addQty`로 수량만 더한다.

**버튼 켜고 끄기**: `setEnabled(false)`면 회색이 되어 못 누른다. 고른 발주가 '요청'일 때만 [입고 처리]·[발주 취소]를 켠다. 잘못된 동작을 화면에서 먼저 막는 방법이다.

**직전 단가 자동 입력**: 품목을 고르면 `lastUnitCost`로 지난번 단가를 찾아 칸에 넣는다. 처음 발주하는 품목이면 빈칸이다.

**말로 설명해 보기**
- 담은 품목을 바로 DB에 저장하지 않는 이유는?
- 입고된 발주의 [입고 처리] 버튼은 왜 꺼져 있나요?

## 12단계 — 다른 팀원에게 기능 빌려주기

**public 메서드는 약속이다**: `decreaseStock(Connection, menuId, qty)`는 ⑥이 쓰는 약속이다. 이름이나 받는 값을 바꾸면 ⑥의 코드가 깨지므로, 바꿀 때는 꼭 먼저 알린다.

**재고를 조건 붙은 UPDATE 한 번으로 빼는 이유**: `UPDATE menu SET stock = stock - ? WHERE menu_id = ? AND stock >= ?`
읽고 → 계산하고 → 쓰는 세 단계로 나누면, 그 사이에 키오스크와 POS에서 동시에 주문이 들어와 재고가 마이너스가 될 수 있다. 조건 붙은 UPDATE 한 번은 DB가 한 번에 처리하므로 안전하다. 바뀐 줄이 0이면 재고 부족이라 예외를 던지고, ⑥은 주문 전체를 rollback 한다.

**말로 설명해 보기**
- 키오스크와 POS에서 마지막 라면을 동시에 주문하면 어떻게 되나요?

## 13단계 — 합치기

**패키지와 이름이 같아야 한다**: 스텁을 지우고 진짜 파일을 넣으면, 진짜 파일의 패키지와 클래스 이름이 스텁과 같아야 내 코드가 그대로 동작한다.

**Ctrl + Shift + O (Organize Imports)**: 필요한 import를 자동으로 넣고 안 쓰는 import를 지운다.

**자주 나는 오류**

| 오류 | 뜻 |
|---|---|
| `cannot be resolved to a type` | 그 클래스를 못 찾음 (파일 없음, 패키지 다름, import 없음) |
| `The method … is undefined` | 그 이름의 메서드가 없음 (약속한 이름과 다름) |
| `Duplicate class` | 같은 이름 클래스가 두 개 (스텁을 안 지움) |

## 14단계 — 통합 테스트

**단위 테스트와 통합 테스트**: 6·7·11단계처럼 내 부분만 시험하는 것이 단위 테스트, 14단계처럼 6명의 화면을 이어서 처음부터 끝까지 해 보는 것이 통합 테스트다. 스텁으로 막아 둔 연결(①의 관리자 번호, ③의 게임 재고, ⑥의 재고 감소)은 통합 테스트에서만 진짜로 확인된다.

**다시 처음부터**: 하나를 고치면 다른 곳이 깨질 수 있어서, 고친 뒤에는 체크리스트를 1번부터 다시 한다.
