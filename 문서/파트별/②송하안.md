## 내 화면

| 화면 | 파일 | 버튼 / 이벤트 → 하는 일 |
|---|---|---|
| 회원 관리 | `MemberPanel` | 검색창(KeyListener) → `MemberDAO.search` (이름 또는 전화 뒤 4자리) / 표 클릭(MouseListener) → 폼 채우기 / [등록] → `insert`(등급 '일반', 포인트 0) / [수정] → `update` (등급·포인트는 안 고침) / [삭제] → 결제 기록 있으면 막기(`hasPayments`), 없으면 `delete` |

결제 팝업은 ⑤의 [이용 종료] 팝업이 `PaymentDialog.open(화면, usageId)`로 연다. 결제가 끝나면 `true`를 돌려준다.

## 내 테이블

| 테이블 | 핵심 칸 | 왜 이렇게 |
|---|---|---|
| `member` (회원) | `phone1~3` UNIQUE, `grade`(일반/실버/골드), `point` | 같은 전화번호 중복 가입을 DB가 막는다. 등급은 결제할 때 자동으로 바뀐다 |
| `payment` (결제) | `usage_id` UNIQUE, `staff_id`, `member_id`, `total_amount`, `card/cash/point_amount`, `earn_point` | 결제 1건 = 1줄. `usage_id` UNIQUE로 같은 이용 건 이중 결제를 DB가 막는다 |
| `payment_detail` (결제 상세) | `item_type`(이용료/메뉴), `menu_id`(이용료면 NULL), `qty`, `unit_price`, `subtotal` | 무엇을 얼마에 팔았는지 항목마다 남긴다. 단가를 저장해 두어 나중에 메뉴 가격이 바뀌어도 영수증이 안 바뀐다 |

헤더(`payment`) + 상세(`payment_detail`) 두 테이블로 나눈 이유: 결제 1건에 항목이 여러 개라서. 상세 소계의 합 = 총액 = 카드 + 현금 + 포인트.

## 핵심 흐름 — 결제 트랜잭션 (`PaymentDAO.pay`)

```
con.setAutoCommit(false)
 ① payment 1줄 INSERT (생성된 pay_id를 RETURN_GENERATED_KEYS로 받음)
 ② 결제 항목마다 payment_detail INSERT
 ③ 회원이면: 포인트 = 원래 − 사용 + 적립, 누적 결제 금액으로 등급 다시 계산 → member UPDATE
 ④ ⑤ TableUsageDAO.finish(con, usageId)   → 이용 상태 '결제완료', 퇴장 시각
    ③ GameDAO.cancelReservations(con, usageId) → 남은 예약 취소
con.commit()   // 하나라도 예외가 나면 catch에서 con.rollback() → 아무것도 저장 안 됨
```

- 남의 메서드에 **같은 `con`** 을 넘겨야 한 트랜잭션으로 묶인다. 받는 쪽은 commit·close를 하지 않는다.
- 이미 결제된 이용 건이면 ①에서 `usage_id` UNIQUE 위반, 또는 ④의 `finish`가 0줄을 바꿔 예외 → rollback.
- 등급: 누적 10만 원 이상 실버, 30만 원 이상 골드. 적립: 카드·현금으로 낸 금액의 1% / 3% / 5% (`gradeOf`, `earnRate`). 계획서 예시: 골드, 카드 20,000 + 현금 2,500 → 1,125P.
